--------------------------------------------------------------------------------
1. WHAT .LEXE IS
--------------------------------------------------------------------------------

`.LEXE` represents an application, not a distribution, ISA, or compatibility
technology. The same `.lexe` file should work on Fedora, Debian, Arch, UshaOS
and other Linux systems. The runtime picks the best execution method the package
policy permits and the host provides. The consumer contract is:

    App.lexe  ->  double-click  ->  works

There is ONE execution system (`lexe`, the CLI, which is the source of truth)
and TWO graphical frontends that expose it without reimplementing it:
`lexe-builder` (developer) and `lexe-ui` (consumer + power user, and the
registered `.lexe` handler).

THE CANONICAL DESIGN REFERENCE is a PDF titled ".LEXE Definitive Architecture
(Expanded)". The user has it. It is the source of truth for design decisions —
do not redesign the architecture; if implementation uncovers a real
contradiction, make the smallest change that preserves the architecture and
document why.

The implemented state of that architecture is written up in
`docs/DEFINITIVE-ARCHITECTURE.md`. READ THAT FIRST — it is the map, it is
current, and its final section states plainly what is NOT done.


--------------------------------------------------------------------------------
2. WHERE THE WORK STANDS
--------------------------------------------------------------------------------

All THREE payload kinds work end to end, each proven by an acceptance suite:

  native    a compiled Linux ELF, run directly — no layer in the steady state
  portable  SOURCE, compiled by the machine that installs it (§5A): approval
            gates the operation, the build runs unprivileged in the launcher's
            sandbox with the network denied, and the output is verified to be a
            host-ISA executable before anything is promoted
  windows   a Windows PE, run through Wine or Proton — and a real Windows
            program really runs, sandboxed and headless

`launch.mode: "service"` detaches for real (a supervisor holds the version's
launch lease; it is NOT a session-manager service, and the runtime says so).
Both graphical frontends can approve a compile. `core/desktop` no longer holds
a second implementation of desktop registration.

Full detail, commit by commit including the bugs found: handoff/SESSION-LOG.md.

--------------------------------------------------------------------------------
6. HOW TO WORK ON THIS CODEBASE
--------------------------------------------------------------------------------

  * Fix root causes, not symptoms. No KDE-specific hacks, no special-case
    scripts. If a shell script and the runtime both implement the same thing,
    that is a bug — the runtime owns it.
  * Be truthful in user-facing text. The codebase deliberately never says
    "verified", "trusted" (unqualified), "safe" or "secure" on its own
    authority — route trust/permission/isolation wording through
    `src/core/presentation.hpp`. When a capability is unavailable, SAY SO with
    a reason rather than omitting it.
  * Each consent authorizes ONE thing. `--yes`, `--accept-permissions`,
    `--trust` and `--approve-compile` are deliberately separate. Do not collapse
    them.
  * When you change a claim, change the test that pinned the old claim — and
    make the new test pin the new truth just as tightly.
  * Persistence is part of correctness. The alpha famously worked on the first
    attempt and then did not survive a reboot. Something working once is not
    done.
  * TRY IT. Both of the things that made the foreign-OS path actually work, and
    the one real memory leak, were found by running something — not by reading
    code. Evidence over reasoning.
