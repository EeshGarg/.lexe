1. WHAT .LEXE IS
--------------------------------------------------------------------------------

`.LEXE` represents an application, not a distribution, ISA, or compatibility
technology. The same `.lexe` file should work on Fedora, Debian, Arch, UshaOS
and other Linux systems. The runtime picks the best execution method the package
policy permits and the host provides. The consumer contract is:

    App.lexe  ->  double-click  ->  works

There is ONE execution system (`lexe`, the CLI, which is the source of truth)
and TWO graphical frontends that expose it without reimplementing it:
`lexe-builder` (developer) and `lexe-ui` (consumer + power user, and the
registered `.lexe` handler).

THE CANONICAL DESIGN REFERENCE is a PDF titled ".LEXE Definitive Architecture
(Expanded)". The user has it. It is the source of truth for design decisions —
do not redesign the architecture; if implementation uncovers a real
contradiction, make the smallest change that preserves the architecture and
document why.

The implemented state of that architecture is written up in
`docs/DEFINITIVE-ARCHITECTURE.md`. READ THAT FIRST — it is the map, it is
current, and its final section states plainly what is NOT done.

5. THE NEXT HIGHEST-PRIORITY WORK
--------------------------------------------------------------------------------

**PORTABLE CODE AND HOST-ISA COMPILATION (§5 + §7 of the PDF).** This is the
largest remaining gap and the clear next piece.

Today `applicationType` accepts only `"native"`. The architecture requires:

        SAME App.lexe
              |
    +---------+---------+
    |         |         |
  x86-64    ARM64    RISC-V
    |         |         |
  compile  compile  compile      <- on the destination machine
    |         |         |
    +---------+---------+
              |
        Native Linux

with `ADMIN COMPILE APPROVAL` gating the operation, the build itself running
UNPRIVILEGED inside an isolated environment, and the result VERIFIED as a
host-ISA native executable. The approval authorizes the operation; it does not
give build code root.

Entry points that already exist and were shaped to accommodate this:
  * `src/core/manifest.cpp` — `applicationType` validation is one place.
  * `src/core/isolation.hpp` — the bubblewrap sandbox can host an unprivileged
    network-denied build; `build_plan()` is pure and testable.
  * `src/core/execpolicy.cpp` — the resolver already has the shape for a
    "portable source -> host ISA compile -> native" path.
  * `src/core/verify.cpp` — the `payload-role` stage is where a portable
    package's SOURCE payload would be validated instead of requiring an ELF.
  * `docs/FORMAT-0.1.md` §5/§6 — the normative spec to extend.

Read `handoff/NEXT-STEPS.md` for the full prioritized list, including the
smaller items (foreign-OS payloads, real cross-ISA hardware validation, service
mode detaching, signer tiers beyond local trust).

    a reason rather than omitting it (see `lexe trust classes`).

    make the new test pin the new truth just as tightly.
