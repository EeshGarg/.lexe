# .LEXE — Linux packaging

Per-user installer that puts the `.LEXE` runtime on your machine and makes
**double-clicking a `.lexe` file work**. Everything installs under `$HOME`
(XDG paths) — no root required.

## What "wiring up the desktop" means here

The installer does **not** hand-roll the desktop registration. It installs the
binaries and then runs:

```sh
lexe integrate
```

The runtime owns the `.lexe` handler entry, the MIME type and the default
association, so there is exactly one implementation of that registration — and
therefore exactly one thing to check and repair afterwards:

```sh
lexe doctor            # what is registered, and what is missing or stale
lexe doctor --repair   # put it back
```

This is deliberate. Desktop integration is **installed system state, not
session state**: it must survive logout, reboot and a desktop restart, and when
it does break it must be diagnosable by name rather than mysterious. A shell
script that duplicated the registration would be a second, silently diverging
copy of it.

## Files

| File | Purpose |
|---|---|
| `install.sh` | Installs `lexe`, `lexe-ui` and `lexe-builder` into `~/.local/bin`, installs the builder's menu entry, runs `lexe integrate`, then verifies with `lexe doctor`. |
| `uninstall.sh` | Runs `lexe integrate --remove`, then removes the binaries and menu entries. Leaves installed applications, their data, launch references and trust records alone. |
| `lexe-builder.desktop` | Menu entry for the package builder (`lexe-builder`). Shows under Development / Utility. |

The `.lexe` handler entry (`lexe-handler.desktop`) and the MIME declaration are
**generated by the runtime**, not shipped as static files — see
`src/lexe/integration/integration.cpp`. They are recorded in
`~/.local/share/lexe/integration.json` with their content hashes so `lexe
doctor` can tell "missing" from "someone edited it".

The alpha shipped `lexe-installer.desktop` and `application-x-lexe.xml` here.
Both are superseded: the consumer frontend is now `lexe-ui`, and the MIME type
is generated with `application/vnd.usha.lexe` as canonical and the alpha's
`application/x-lexe` kept as an alias. `install.sh` removes the stale files if
an older install left them behind.

## Install

First build the runtime (GUI enabled so `lexe-ui` and `lexe-builder` are
produced):

```sh
cmake -S . -B build -G Ninja -DLEXE_BUILD_GUI=ON
cmake --build build
```

Then run the installer, optionally pointing it at a non-default build dir:

```sh
./packaging/install.sh          # one line: uses ./build
./packaging/install.sh out/rel  # uses ./out/rel
```

`lexe` alone is enough to use the whole platform; `lexe-ui` and `lexe-builder`
are skipped with a note when GTK 3 development files are absent.

## Verify

```sh
lexe doctor
```

reports the handler registration, the default association, every installed
application's menu entry and `run.lexe` launch reference, the isolation
backend, the terminal policy for console applications, and which compatibility
providers are present. Anything missing or modified is named individually.

## Uninstall

```sh
./packaging/uninstall.sh
```

Removes the runtime. It does **not** remove applications you installed, their
data, their launch references, your trust records, diagnostics or compatibility
preferences — those are yours. To remove an application, do it through the
runtime *before* uninstalling:
Removes the three binaries, both `.desktop` files and the MIME XML, clears the
default-handler association, and refreshes the databases. Installed application
data under `~/.local/share/lexe` is intentionally left in place. It reports what
it actually removed — on a machine where the runtime was never installed it says
so rather than announcing a removal that did not happen. If `LEXE_HOME` is set it
also clears the confined copy described below, so nothing `lexe integrate` wrote
survives an uninstall that claims to have removed it.

## `LEXE_HOME` and desktop registration

A desktop environment reads `.desktop` entries and MIME packages from
`$XDG_DATA_HOME` (default `~/.local/share`) and nowhere else. `install.sh` always
writes there, whatever `LEXE_HOME` says.

`lexe integrate` is different, and deliberately so: when `LEXE_HOME` is set it
confines its writes to `$LEXE_HOME/applications` and `$LEXE_HOME/mime/packages`,
because `LEXE_HOME` is exactly how the test suite and the demos keep out of your
real profile, and nothing in the environment tells a test run apart from an
install under a custom `LEXE_HOME`. The files are still written, and they are
still correct — no desktop just ever looks at them. The command says so instead
of reporting a registration (`IntegrationResult::note` in
`src/lexe/integration/desktop.hpp`).

So if you keep a custom `LEXE_HOME` and want the double-click association, run
either of these — the two files contain no `LEXE_HOME`-dependent paths, so a
registration made without it is correct for your custom install too:

```sh
./packaging/install.sh          # writes to $XDG_DATA_HOME regardless
env -u LEXE_HOME lexe integrate # same two files, same two destinations
```

```sh
lexe remove <app-id> --purge-data
```
